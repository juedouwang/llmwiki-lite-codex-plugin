## Purpose

让科研人员在所属项目网页中直接理解代码版本的来龙去脉，完成保存、分支实验、合并、恢复和远端同步。界面保持用户已确认的简约形态，所有仓库变更均来自明确点击，保留已有工作与历史，不要求用户先学会命令行 Git，也不自动替代科研判断。

## ADDED Requirements

### Requirement: G-01 项目与仓库边界明确

系统 SHALL 沿用项目“代码”入口，仅操作该项目注册源目录对应的普通单工作树仓库。项目切换后仓库状态、详情、未提交输入和操作目标不得串用。源目录不是仓库根目录、Git 不可用或仓库不支持写操作时，系统 SHALL 展示具体原因，不自动初始化、克隆或改绑父级仓库。

#### Scenario: A-01 切换科研项目
- **WHEN** 用户从项目 A 切换至项目 B 的代码页
- **THEN** 展示 B 的分支和版本，清除 A 的操作弹窗；A 的延迟返回结果不得覆盖 B。

#### Scenario: A-02 不支持的仓库状态
- **WHEN** 源目录非仓库、位于父仓库的子目录，或仓库是 bare、多 worktree、涉及子模块或 LFS 的首版不支持状态
- **THEN** 显示相应空态或只读状态及原因，不执行任何写入，不把“父目录能找到 .git”当作对父仓库的操作授权。

#### Scenario: A-03 尚无提交或 HEAD 游离
- **WHEN** 普通仓库尚无提交，或用户从外部将 HEAD 置于游离状态
- **THEN** 空仓库允许选择文件创建首个版本；游离状态允许浏览和从节点建分支，但在切至本地分支前禁用保存、合并、恢复和上传。

### Requirement: G-02 固定已确认的简约页面

系统 SHALL 以已确认整站原型中的代码栏目作为视觉基准，沿用第二份统一共享侧栏、上方分支/合并/拉取/上传工具条、一条工作区修改摘要、中部真实提交图、可关闭的版本详情。不增加仪表盘、指标卡片、常驻多栏操作表单或第二套全局导航。实际项目页 SHALL 接入统一六栏目，代码名称不再是“代码图谱”；本 change 不重新设计其他模块。

#### Scenario: A-04 默认打开代码页
- **WHEN** 页面加载完成且存在当前版本
- **THEN** 选中当前 HEAD，显示其详情；工作区只显示修改文件数和“查看并保存”，未点击时不铺满文件列表；无改动时显示“所有修改已保存”。

#### Scenario: A-05 收起详情与窄屏
- **WHEN** 用户关闭详情或在 320px 至 580px 宽度查看页面
- **THEN** 关闭后图占据可用空间；再次点节点打开详情；窄屏详情移到图下方，操作可换行且没有页面级横向溢出。

### Requirement: G-03 提交图反映真实父子关系

系统 SHALL 绘制本地分支和已缓存远端分支可达提交的真实关系，标出当前分支、其他分支和远端引用。节点展示标题、短哈希、次要时间；时间和作者完整值在详情可查。图首批加载 100 条，点击“加载更早版本”逐批追加，不自动拉取网络或伪造未加载的父节点。

#### Scenario: A-06 分支与合并节点
- **WHEN** 仓库具有两个分叉分支及一个合并提交
- **THEN** 图中分别连接真实父节点，合并节点保留两个父连接；点击某行、其节点或标题选中同一提交，而不是根据提交说明猜测关系。

#### Scenario: A-07 追加历史期间仓库变化
- **WHEN** 用户加载更早版本，期间外部工具新增提交或移动分支
- **THEN** 不拼接两份不同图快照；提示刷新版本记录，保留尚未提交的表单输入，重新取得一致的图。

### Requirement: G-04 点击节点即看版本和文件差异

系统 SHALL 在详情显示所选提交的说明、完整哈希、作者、提交时间和变更文件。普通提交以其父版本为基准，首提交以空树为基准，合并提交默认以第一父版本为基准并标明。点击文件显示真实统一差异；文件路径和内容作为文本展示，不执行其中的代码或 HTML。

#### Scenario: A-08 选择历史文件
- **WHEN** 用户切换节点并点击其某个修改文件
- **THEN** 文件列表及差异均来自该节点，不混入当前工作区内容；新增、删除和重命名能分辨。

#### Scenario: A-09 二进制或超大差异
- **WHEN** 选中文件是二进制、非支持文本编码或差异超过规定展示上限
- **THEN** 展示文件名、变化类型与“二进制文件”“暂不支持此编码”或“差异过大”说明；若展示截取内容，明确标记截断，不伪装成完整差异。

### Requirement: G-05 只保存用户选择的完整文件

系统 SHALL 用“查看并保存”打开保存弹窗：变更文件复选框、可查看的差异、版本说明和“保存到本地”。首次打开默认全选非忽略的变更文件；至少选一项且说明去除首尾空白后为 1–4000 字符。首版按完整文件保存，包括选中文件当前的全部工作区修改，不提供行级暂存；外部已暂存状态须可识别，不静默夹带未选文件。

#### Scenario: A-10 选择部分文件保存
- **WHEN** 工作区有 A、B、C 三个变更文件，B 已在外部暂存，用户只选择 A 并填写说明保存
- **THEN** 新提交只包含 A；B 的暂存内容与 C 的工作区内容保持不变；图出现新节点，剩余修改仍可继续保存，远端不变化。

#### Scenario: A-11 文件部分暂存
- **WHEN** 所选文件同时有已暂存和未暂存改动
- **THEN** 保存前明确提示“将保存该文件当前全部修改”；提交当前完整文件，不把用户误导成仅保存已暂存部分。

#### Scenario: A-12 新增删除重命名与失败保留
- **WHEN** 用户选择新增、删除或重命名文件，或提交失败
- **THEN** 成功时对应变化准确入版本，重命名按旧/新路径一组选择；失败时不丢文件和说明，不自动回退或丢弃暂存内容，刷新实际状态后说明是否已有文件进入暂存区。

### Requirement: G-06 创建和切换分支不混淆

系统 SHALL 提供当前分支下拉列表和“新建分支”，以及节点详情中的“从此创建分支”。创建只新增指定提交上的分支，不自动切换、不自动上传；切换通过分支列表明确选择。名称遵从 Git 分支名称规则，不采用示意数据中的简化命名限制。

#### Scenario: A-13 从历史节点创建实验分支
- **WHEN** 用户在历史节点选择“从此创建分支”并输入合法且未使用的名称
- **THEN** 新分支指向该节点，当前分支和文件均不变化，图出现其分支标签，界面说明“已创建，仍在当前分支”。

#### Scenario: A-14 切换分支有未保存修改
- **WHEN** 工作区存在已暂存、未暂存或非忽略的未跟踪文件，用户尝试切换
- **THEN** 停止切换，展示“先保存当前修改”并提供进入保存弹窗的按钮；不得 stash、丢弃或带着修改继续切换。保存后由用户重新发起切换，不自动连带执行。

### Requirement: G-07 合并方向和结果可理解

系统 SHALL 以当前本地分支为目标，让用户选择另一本地分支并确认“将 X 合并到 Y”。开始前要求干净工作区。可快进时移动目标指针且说明“已快进”；已包含时说明“无需合并”；双方分叉时进行普通合并，不做 rebase、不删除源分支、不自动上传。

#### Scenario: A-15 无冲突合并
- **WHEN** 用户确认合并没有文本冲突的两个分叉分支
- **THEN** 新提交具有两个正确父节点；当前分支包含两边的修改，原实验分支保留，界面可立即查看结果。

#### Scenario: A-16 快进或没有新内容
- **WHEN** 源分支可快进或已包含在当前分支中
- **THEN** 分别完成快进或保持无变化，不为了显示动画制造空合并提交。

### Requirement: G-08 普通文本冲突可在网页解决或取消

系统 SHALL 在冲突发生后展示一个专用处理区，不把冲突当普通失败消失。首版支持两边修改同一个既有 UTF-8 普通文本文件、两边及结果均不超过 1 MiB 的冲突：逐文件查看“当前分支内容 / 合入分支内容 / 最终内容”，可选择一边的完整文件或编辑最终内容，再明确标记该文件已解决。全部文件解决后才可“完成合并”；允许“取消本次合并”。

#### Scenario: A-17 编辑并完成普通文本冲突
- **WHEN** 用户查看冲突，选择一边或编辑最终内容并逐文件确认，然后完成合并
- **THEN** 只有确认的最终内容进入提交；遗留冲突标记会阻止完成；操作期间保存/切换/再次合并/恢复被禁用，成功后恢复普通页面。

#### Scenario: A-18 刷新与取消本次合并
- **WHEN** 用户刷新仍在处理本网站发起的合并，或点击“取消本次合并”并确认
- **THEN** 刷新后仍能找到冲突及已保存的解决结果；取消时恢复合并前的 HEAD、索引和受跟踪文件，提示放弃本次冲突处理结果，不删除额外出现的未跟踪文件。

#### Scenario: A-19 非支持冲突与外部操作
- **WHEN** 冲突包含二进制、删除/修改、添加/添加、重命名、超大或非 UTF-8 文件，或合并/rebase 由其他工具发起
- **THEN** 列出类型和文件，不伪装成网页可解决；本网站发起的合并仍能取消；外部操作仅显示“请在原工具完成或取消后刷新”，不自动接管、覆盖或中止。

### Requirement: G-09 恢复旧代码必须保留历史

系统 SHALL 将“恢复到此版本”定义为：让当前分支全部受跟踪文件达到目标提交的树状态，再创建一个以原 HEAD 为父的新提交。执行前展示目标、当前分支、将新增/修改/删除的文件及差异，明确“历史保留，不自动上传”，并由用户确认。恢复不是撤销单个提交，也不是移动分支到旧节点。

#### Scenario: A-20 恢复历史版本
- **WHEN** 用户确认从当前 H 恢复到历史 T，且工作区干净
- **THEN** 生成 R，满足 R 的唯一父为 H 且 R 的树等于 T 的树；H 及其历史仍可达，当前分支不变，未跟踪/忽略文件不被删除，远端不变化。

#### Scenario: A-21 相同内容或文件覆盖风险
- **WHEN** 当前树已等于目标，或目标会覆盖忽略/未跟踪文件
- **THEN** 相同内容不创建空提交；有覆盖风险时列出冲突路径并停止，不自动删除、备份搬移或忽略风险继续执行。

#### Scenario: A-22 恢复后的提交失败
- **WHEN** 文件恢复步骤已经完成，但新提交未成功产生
- **THEN** 明确标为“文件已恢复，但版本尚未保存”，展示真实工作区并保留变化，让用户修复原因后保存；不得显示恢复成功或自动 hard reset。

### Requirement: G-10 远端由用户确认而非猜测

系统 SHALL 使用仓库已有远端和跟踪配置。当前分支已有 upstream 时显示它；没有时要求在已有远端中选择目标分支，不默认等同于 origin/main。首版不提供新建/编辑远端或托管平台登录。目标地址须隐藏口令、token 和 URL 用户信息。

#### Scenario: A-23 多远端或尚无 upstream
- **WHEN** 仓库有多个远端，当前分支无跟踪目标
- **THEN** 拉取/上传前要求选定远端及目标分支；用户确认目标前不发送网络请求，不向错误远端试探上传。

#### Scenario: A-24 没有远端
- **WHEN** 仓库没有配置远端
- **THEN** 本地保存、分支、合并与恢复仍可使用；拉取/上传显示“尚未配置远端，请先在现有 Git 工具中配置”，不索要令牌或自动创建 GitHub 仓库。

### Requirement: G-11 拉取区分检查和更新代码

系统 SHALL 在点击“拉取”后展示目标和“检查远端更新”。只有用户明确检查时才读取远端；检查只更新远端跟踪信息，不改变本地 HEAD、索引和工作区。结果展示“已最新”“可快进”“已分叉”及相关提交；需要更新代码时必须再次点击“更新当前分支”或“合并远端更新”，复用干净工作区要求和合并/冲突流程。

#### Scenario: A-25 检查后可快进
- **WHEN** 用户检查远端发现本地落后但没有分叉
- **THEN** 先显示新提交，取消弹窗不改变本地代码；确认更新后快进到刚检查的目标，保留原提交历史。

#### Scenario: A-26 分叉拉取或网络失败
- **WHEN** 检查发现双方分叉，或读取远端失败
- **THEN** 分叉时明确进入普通合并确认，不执行 rebase；失败时保留本地代码并提供可理解的重试原因，远端信息标为旧缓存而非“已同步”。

### Requirement: G-12 上传是单分支的普通推送

系统 SHALL 在上传确认框中展示当前本地分支、目标远端/分支和待上传提交；确认后只普通推送这一分支，不带其他分支、标签或未提交文件，不强推。首次向不存在的目标分支上传须标明“将新建远端分支”；成功后才能记为跟踪关系或已上传。

#### Scenario: A-27 保存与上传明确分离
- **WHEN** 用户保存了两个本地版本而尚未点击确认上传
- **THEN** 待上传计数变化但远端引用不变；明确上传成功后更新状态，未提交的工作区内容不上传。

#### Scenario: A-28 远端拒绝或回执不明确
- **WHEN** 远端发生非快进拒绝、认证失败，或连接中断无法确定推送结果
- **THEN** 分别提示先检查/拉取、在原工具完成认证、或“上传结果待核对”；不强推、不循环重试、不把通信中断直接认定为远端未更新。

### Requirement: G-13 执行前复核且不误伤其他工作

系统 SHALL 在写操作前复核当前项目、仓库、HEAD、索引、相关文件内容及源/目标分支版本。预览后材料已变化时停止此次执行，刷新影响供用户确认，同时保留输入。相同仓库的网页写操作串行；不能用只有文件名/修改标记而没有内容的检查代替版本复核。

#### Scenario: A-29 预览后同一文件再次修改
- **WHEN** 保存或恢复确认框已打开，外部 agent 再次修改一个已为 modified 的相关文件
- **THEN** 确认操作被拒绝并显示“内容已变化，请重新查看”，不因为 modified 标记没变而错误接受旧确认。

#### Scenario: A-30 越界或重复点击
- **WHEN** 请求包含其他项目路径、越界路径、伪造引用，或用户重复点击/另一个标签页同时写同一仓库
- **THEN** 越界请求无写入；同仓库冲突操作返回可重试提示或旧状态提示，不重复创建提交；输入和已有文件保留。

### Requirement: G-14 低打扰与实际状态反馈

系统 SHALL 只在点击后执行相应 Git 操作，页面加载、定时刷新、Hook 和节点选择不触发网络同步、后台模型或自动提交。所有本地进程无可见终端；需要交互认证、签名或仓库自定义执行器而无法保证非交互时，显示限制，不绕过仓库策略或启动外部窗口。当前操作进行中仅禁用相关写按钮，不遮挡阅读其他项目/内容。

#### Scenario: A-31 不打扰桌面工作
- **WHEN** 用户进入代码页、保存、合并、恢复或遇到认证失败
- **THEN** 不启动 codex exec，不弹 PowerShell/cmd、Git Bash、编辑器或认证浏览器窗口；错误保留在当前操作附近，不反复弹窗。

#### Scenario: A-32 页面速度与外部变更
- **WHEN** 页面在本地性能基准仓库运行，或从其他应用回到已打开的代码页
- **THEN** 按钮点击 100ms 内显示忙碌反馈；基准首屏状态及前100条版本的可交互时长按5次测量中位数不超过2秒；回到页面刷新本地状态但不丢表单和冲突编辑草稿，不后台定时拉取网络。

### Requirement: G-15 缺少作者身份时能在网页修正

系统 SHALL 在需要提交但仓库缺少可用作者名称或邮箱时，提供名称/邮箱输入及“仅用于当前仓库”提示。仅用户确认后写当前仓库本地配置，不改全局身份、不猜测真实姓名邮箱，不要求为浏览版本先填写。

#### Scenario: A-33 首次保存缺少身份
- **WHEN** 用户准备保存而仓库与全局均未设置身份
- **THEN** 保存说明和文件选择保留；用户填写并确认当前仓库身份后，可以重新点击保存，无需退出页面执行命令。

### Requirement: G-16 与科研记录及既有功能分开

系统 SHALL 将提交、合并、恢复的结果显示为 Git 事实，不自动完成任务、不将代码提交当成实验成功，不为 Git 另建日报/知识库维护任务。已存在的项目文件/提交采集路径可在下次增量或每日整理读取结果；未接入则明确未接入，不阻塞本次 Git 操作。

#### Scenario: A-34 Git 操作与科研推理解耦
- **WHEN** 用户成功保存、合并或恢复，或每日总结暂不可用
- **THEN** 操作完成立即返回；Todo 状态、日报正式版和知识正文不被该操作改写，不同步等待模型或宣称科研结论已验证。

### Requirement: G-17 验收须证明网页真正可操作

交付 SHALL 包含真实临时仓库的浏览器端到端证据及 Git 结果断言，不得只用静态图、前端模拟、直接调用函数或勾选任务宣称完成。生产页面不得保留示意项目、固定哈希、“演示成功”假反馈或与真实仓库不一致的数字。

#### Scenario: A-35 不使用终端的本地完整流程
- **WHEN** 验收者通过网页完成“选文件保存 → 建分支并切换 → 保存实验 → 切回主线 → 合并 → 查看旧节点 → 恢复”
- **THEN** 每一步都真实写入临时仓库；原提交仍可达，合并父关系正确，恢复树等于目标；不要求验收者在终端补做主要操作。

#### Scenario: A-36 同步与回归证据
- **WHEN** 通过临时 bare 远端验证拉取、普通上传及拒绝场景，且运行已有项目进度/笔记/文献/知识浏览回归
- **THEN** 报告明确哪些是本地远端测试、哪些是真实 GitHub 验证；未获授权时不接入真实 GitHub；已有功能通过才算集成完成。

### Requirement: G-18 整站原型中的代码栏目真实接入

系统 SHALL 保持已确认整站源稿的代码布局、完整线性分支图标和节点交互；项目切换、版本详情、合并/恢复等均接真实仓库状态，不能让原型的模拟操作或截图替代真实结果。统一导航不扩大 Git 授权，不增加自动执行或隐藏后台。

#### Scenario: A-37 整站入口及真实仓库交互
- **WHEN** 用户从其他栏目进入代码、选择节点、在临时仓库完成保存/合并/恢复，再切换项目返回
- **THEN** 共享壳与确认源稿一致，图标圆环无遗漏，图和操作结果与 Git 后置断言一致，项目数据不串用；原 A-35/A-36 仍必须通过。
