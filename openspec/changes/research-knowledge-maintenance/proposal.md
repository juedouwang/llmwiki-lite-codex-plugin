## Why

现有 LLM Wiki 已有变化检测、Markdown 知识页和维护 Skill，但用户仍需要主动要求维护，改写旧知识也没有统一的网页确认流程。需要在不影响科研工作和日报生成的前提下，让新增知识自动沉淀、原有内容的修改由用户确认，而不是重建知识库。

## What Changes

- 每日与第二份报告功能共用既有定时入口；日报和知识维护独立取材、独立记录结果。支持在对话中明确要求立即维护，不增加 Git 提交即时触发。
- 只处理新增、变化或尚未处理的材料；宿主 AI 判断是否值得形成项目架构、运行流程、术语、方法及有依据的长期认识。无新知识可跳过，不制造空白分类或流水账。
- 自动新建知识页或在原文末尾补充不冲突的新内容；任何改写、删减、调整原有内容的操作一律成为待确认建议，不因为原文由 AI 写就允许覆盖。
- 复用知识库与知识阅读页面，对齐已确认原型的目录/阅读区与显式 Markdown 编辑；保留轻量待确认入口，用户点击后查看原文、建议、原因和依据，仅提供“采用修改”“保留原文”两个确认动作。
- 同页同依据被拒绝后不重复催促；原文或依据改变使建议失效时禁止旧结果覆盖，重新检查。检查时间、实际更新时间和来源放详情，不污染正文。
- 只增加小型状态/建议存储、确定性工具和网页接入；不建数据库、通用作业系统、模型服务或常驻执行器。

### 已确认界面对齐增量

共享壳及原型只引用第二份 design D-11；本份承担知识目录/阅读、来源、维护设置与手动编辑接线。已实现维护协议不重写，已完成任务不重勾，新 UI 验收在 tasks 第6节。手动修改是明确用户操作，不给后台增加覆盖权限。

## Capabilities

### New Capabilities

- `research-knowledge-maintenance`: 增量取材、每日及按需维护、自动新增与旧内容确认、来源追溯、拒绝去重、调度隔离和非阻塞体验。

### Modified Capabilities

无。`openspec list --specs` 当前未发现主规格。本 change 不改动第一份 `research-progress-todo-done` 的语义；与尚未实施的第二份 `research-daily-weekly-reports` 的共享计划接入约定见 design 的 D-02。第二份报告生成器仍不能修改知识库，第三份只在调度外层增加独立阶段，不把两种产物混写。

## Impact

- 实施仓库：`E:\GitHub\llm-wiki-agent\next\llmwiki-lite-codex-plugin`。本次只生成规划材料，代码实施、真实自动任务启用另行授权。
- 复用 `llmwiki_core.py` 的忽略、路径、哈希和 Wiki 结构检查，`research_records.py` 的记录读取，`research_web_ui.py` 的知识页以及既有 Markdown 渲染。
- 新增 `knowledge_maintenance.py`、少量网页资源、3 个 MCP 工具及针对性测试；最小接入 `web_server.py`、`mcp_server.py`、报告设置和共享任务提示词，更新维护 Skill/网页 Skill/README。
- 成熟知识继续写入既有 Wiki；检测基线、运行记录、候选和依据元数据留在注册项目 state 目录，不使用知识页保存机器状态。
- 与第一、二份涉及同一网页/MCP/服务文件；统一交接后顺序实施，不覆盖其他 agent 的在途改动。验收使用临时项目，不改真实科研数据或插件缓存。

## Non-goals

不改 Todo/Done，不代写日报周报，不改文献目录或阅读笔记；不自动下载论文，不接入新聊天采集器，不扫描用户全部会话；不做 Git 提交触发、Git 写操作、自动部署/发布；不加知识图谱、固定分类体系、新的富文本编辑器框架、版本管理平台或每条知识的复杂状态机。历史 Wiki 不迁移、不批量重写。
